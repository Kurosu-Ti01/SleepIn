# 为一所学校编写导入方案

这篇文档讲的是**一件具体的活**：拿到一所学校（或一个同学反馈的教务系统），把它变成应用里可选的一条导入方案，
并且能判断出「跑不通时是哪一段有问题」。

- 接口与文件格式的参考手册在**预设仓库的 README**里（族、`config`、`ctx` 的全部成员、载荷形状、周次规则、发布与 CI）。
  本文不重复那些表，而是讲**顺序、判断与排查**。
- 应用侧的机制（载荷校验、桥协议、导入页面、落库）见 [教务系统导入实现](./6.portal-import.md)。
- 已经有现成的方案时，用户侧的操作见用户文档 `docs/SleepIn-Docs/docs/user/portal-import.md`。

## 1. 先分清三段链路

导入失败的原因一定落在这三段之一。**先确定是哪一段，再去看代码**，否则很容易在错误的地方翻半天。

| 段 | 回答什么 | 实现 | 失败时用户看到 |
| --- | --- | --- | --- |
| **预设** | 从哪来、叫什么、起始网址 | 应用内的来源 + 索引解析 | 「该方案的脚本无法读取」「找不到该导入方案」 |
| **脚本** | 怎么取数、字段在哪 | 在 WebView 里跑（族适配器 + 运行流程） | 「认不出这个教务系统」「适配器缺少必需的环节」「读取课表失败」 |
| **载荷** | 取出什么 | 应用校验并落库 | 确认弹窗里的三条诊断提示；或「导入数据里没有任何课程」 |

一个实用的判据：**脚本的报错都带着自己「看见了什么」**（当前页面路径、缺失的环节名、跳过的行数），
而**预设段的报错只说文件读不到**。看到后者就别去调适配器。

## 2. 动手前要拿到的六个事实

侦察用桌面浏览器打开目标教务系统就够了，不需要写代码。要拿到的是：

| 事实 | 从哪拿 | 为什么必须知道 |
| --- | --- | --- |
| 1. 登录页地址 | 地址栏 | `preset.json` 的 `startUrl`（必须 `https://`） |
| 2. 课表页地址 | 手动点到课表页后看地址栏 | 写进方案的 `description`，也用来确认用户的起始路径 |
| 3. 课表数据从哪来 | DevTools → Network → 在课表页刷新 | 是 XHR/JSON 还是服务端渲染的 HTML？**这一步决定族的归属** |
| 4. 响应里的字段名 | Network → Response | 族 `config.fields` 的值（`kcmc` 还是 `courseName`） |
| 5. 学期参数从哪来 | Network → 请求的 Payload/Query | 是接口给的，还是页面上「学年学期」下拉框里的？ |
| 6. 是否报上课时间 | 响应里有没有起止时刻 | 决定要不要写 `timeSlots`（写了才有「用方案提供的作息表」选项） |

三个容易漏的点：

- **课表在 iframe 里**：Network 面板里那条请求的发起者不是顶层文档。这类系统需要单独处理，通用抓取也读不到。
- **接口地址带查询参数**（如 `?gnmkdm=N2151`）：`config` 里通常要把路径和参数分开写。
- **同一个系统有多个子形态**（如金智的 `wdkb` / `kbapp`）：先判断该部署用的是哪一个，再决定是加变化点还是加子形态。

## 3. 选形态：先问「这些事实指向哪个族」

按顺序问自己：

1. **有没有已适配的族覆盖这个系统？** 看预设仓库 README 的族表与各族的 `CHANGEPOINTS.md`。
   有 → 形态 A，**不写任何 JS**。
2. **这个族能覆盖，但有一处逻辑不同？** → 先找 `CHANGEPOINTS.md` 里有没有对应的取值。
   **能变成取值就一定变成取值**（下一所学校可以直接复用）；确实不能时才加 `override.js`（形态 B）。
3. **都不是？** → 形态 C，自己写脚本。这时仍建议以 `lib/runner.js` 为起点：桥交互、周次解析、
   时段合并、载荷组装都不用重写。

> 判断的顺序是有代价的：形态 A 的贡献只需要审几个字段；形态 B 要审一段任意代码；形态 C 要审一整份。
> 所以「能不能变成取值」不是风格问题，而是**审阅成本**问题。

## 4. 形态 A：只写一行取值

```powershell
Copy-Item -Recurse presets/_example presets/<schoolId>
Copy-Item -Recurse schools/_example schools/<schoolId>
```

`preset.json` 里每一项的含义：

| 字段 | 注意 |
| --- | --- |
| `id`（目录名） | `^[a-z0-9][a-z0-9-]{1,63}$`；会成为路径的一部分，改名等于换一个方案 |
| `name` | 列表里显示的名字，建议写成「学校名 · 教务类型」，多条方案靠它区分 |
| `schoolId` | 必须与 `schools/` 下的目录名一致，否则生成器报错 |
| `group` | `UNDERGRADUATE` / `POSTGRADUATE` / `GENERAL`。**同一个学校可以有多份方案**（本科/研究生教务分开），靠这个字段分组 |
| `initial` | 单个大写字母，用于列表分组与搜索 |
| `startUrl` | 登录页，必须 `https://` |
| `family` | 族 id；留空则必须自己提供 `script.js` |
| `config` | **只写与族默认值不同的项**。键名必须存在于 `family.json` 的 `changePoints`，否则生成器报错 |
| `description` | 适用系统、使用前提、已知限制。用户在方案列表里看得到 |
| `maintainer` | 你的 GitHub ID，便于反馈问题 |

`config` 是这套结构的核心：**同一族的第二所学校正常情况下只需要改几个值**。
逐项对照 `families/<id>/CHANGEPOINTS.md`，把每所学校的差异写进对应的变化点。

`schools/<schoolId>/school.json` 一般只需要四个字段：`id`（与目录名一致）、`name`（必填）、
`code`（官方学校代码，用于显示与搜索，不确定就省略）、`aliases`（用户可能输入的简称与旧校名，
搜索时按「包含」匹配，写全一点更容易被搜到）。

## 5. 形态 B / C：什么时候必须写代码

**形态 B（`override.js`）** 适合「族里 100% 的逻辑都对，只有一处不对」。写法是只重新定义那一个环节，
其余仍用族适配器的实现：

```js
// 为什么要覆盖：该部署的课表接口把「第几节」写成 1-2 这种字符串，而族的默认实现按数字读。
const presetOverrides = {
  normalizeRow(row, ctx) { /* … 只改这一处 … */ }
};
```

**形态 C（完整脚本）** 适合完全异构的系统（例如课表页根本没有可用的接口，只能解析 HTML）。
此时也建议复用 `lib/runner.js`：它已经把桥交互、周次解析、时段合并、载荷组装做完了，
自己写的是 `detect` / `listSemesters` / `fetchSchedule` / `normalizeRow` 这几个环节。

## 6. 在应用里验证

**DevTools 试跑能验证解析对不对，但不能代替在应用里跑一遍**：应用还要做载荷校验、弹确认框、写数据库。
真正算数的验证是在应用里走完一次成功的导入。

最短路径：

1. `.\gradlew assembleDebug` 并安装。
2. 把方案放进应用。两种方式：
   - **自己写的方案**：设置 → 教务导入 → 「导入课程表」→ 右下角 `＋` →「导入自己的脚本」，粘贴脚本；
   - **发布格式的源**：把仓库目录拷进手机，用「从本地目录导入源」选那个目录（比走网络快，且同样逐文件校验哈希）。
3. 走一遍正常流程：选方案 → 选目标与作息表 → 开始导入 → 登录 → 打开课表页 → 执行导入 → 确认 → 完成。
4. **回来核对课表**：门数、每门课的时段、周次、地点是否与教务系统一致。

如果你想在没有真实教务系统的前提下确认**导入链路本身**没坏，debug 构建里有一个「模拟导入（仅调试版）」预设，
它产出三种固定的样例载荷。用法见 [Windows 构建与调试](./../1.build-debug/1.build-debug-windows.md)。

### 6.1 确认弹窗逐项核对

| 显示项 | 该核对什么 |
| --- | --- |
| 周数 | 弹窗里是「第 X-Y 周（课程表共 N 周）」。与学校日历不一致时先查 `semesterMeta` 的 `totalWeeks` / `startDate`；**错了会让整张表看起来「这周没课」** |
| 课程 / 课时 | 门数是否与你看到的一致；课时数明显偏少通常意味着有行被跳过 |
| 作息表 | 选「用方案提供的」之前，先看它是不是真的报回了时间（弹窗会显示「新建作息表（来自方案，N 节）」） |
| 目标 | 别把测试数据写进正在用的课程表 |

### 6.2 三条诊断提示的含义

它们**都不是失败**，数据已经写进去了：

| 提示 | 说明 | 该改什么 |
| --- | --- | --- |
| 第 N 节未在所选作息表中定义 | 课时引用了作息表没定义的节次 | 先核对节次是否解析正确；正确就去补全作息表 |
| 第 N 周超出课程表的 M 周 | 学期总周数或开学日期不对 | 修 `timeSlots` 之外，通常是 `semesterMeta.totalWeeks` / `startDate` |
| 有 N 组课时时间重叠 | 载荷内部两门课占了同一时段同一周次 | 常见于调课未合并、或教学班分组不对 |

第三条尤其值得追：它往往意味着 `groupKey` 或调课合并做错了，而不是教务系统真的在冲突。

### 6.3 跳过的行在哪里能看到

这是当前的一个**已知缺口**，写下避免白找：

- **应用里只在一种情况下会告诉你**：一行都没能组成课程时，会弹「没有解析出课程」，并附上跳过行数与原因（最多 5 条）。
- **能解析出一部分时，被跳过的行不会提示**。用户只看到「解析出 N 门课程、M 条课时」。
- 所以**部分跳过要靠 DevTools 试跑摘要发现**：把脚本粘进教务系统页面的控制台，看 `跳过的行` 与 `跳过原因`。
- 运行流程的 `ctx.log` 输出目前只进 WebView 控制台（应用侧的桥没有 `log` 操作），
  需要在应用里看日志时用 `chrome://inspect` 远程调试。

因此：**方案发布前一定要在真实系统上看一次试跑摘要**，不要只看应用里有没有报错。

## 7. 排查表

| 现象 | 常见原因 | 看哪里 |
| --- | --- | --- |
| 「认不出这个教务系统」 | 页面不对、还没登录、`detect` 条件写得过窄 | `detect` 的返回值会附上当前页面路径；对照它改条件 |
| 「适配器缺少必需的环节」 | 适配器漏了必需成员，或名字打错 | 运行流程会列出缺了哪几个 |
| 「这个学期没有课表数据」 | 学期参数不对，或接口返回了空数组 | Network 里那个请求的参数与响应 |
| 「没有解析出课程」 | 字段映射全错、周次全部解析失败 | 弹窗里的跳过原因基本就指向了字段名 |
| 课程数对，但课时数偏少 | 有行被跳过 | 试跑摘要的 `跳过的行`（见 6.3） |
| 同一门课被拆成两门 | `groupKey` 用了时段而不是课程身份 | 预设仓库 README 的 6.3 节（`normalizeRow` 的返回约定，`groupKey` 一段） |
| 多门课被并成一门 | `groupKey` 用了课程名，但教务按教学班分别报 | 改成教学班 id 或「课程名 + 教师」 |
| 周次对不上 | `weeksEncoding` 选错（位图当成文本），或解析抛错被跳过 | 试跑摘要；周次解析**该抛错就抛错**，不会静默算错 |
| 节次对不上 | 把行头里的时刻当成了节次（见第 8 节） | 用 `ctx.parseSections` 而不是自己抓数字 |
| 页面显示错乱、按钮点不到 | 教务系统只认桌面版 UA | 导入页右上角「更多」→ 桌面版 UA |
| `net::ERR_CLEARTEXT_NOT_PERMITTED` | 明文 HTTP 且域名不在 `.edu.cn` 内 | 优先改 HTTPS（见 [6.portal-import](./6.portal-import.md) §7.5） |
| 导入后课表「这周没课」 | 开学日期或总周数不对 | 确认弹窗的周数 |

## 8. 一个真实的坑：行头里的时刻

实测里踩到过的一次：课表的行头写成 `第1-2节 08:00-09:40`，
而适配器直接 `match(/\d+/g)` 抓数字，于是把 `08:00` 当成了节次。

改法是在抓数字**之前**先把时刻摘掉：

```js
const withoutTimes = text.replace(/\d{1,2}:\d{2}(?::\d{2})?/g, ' ');
```

这也是运行流程里 `ctx.parseSections` 的做法。**用 `ctx.parseSections(text)` 而不是自己写数字匹配**，
它同时处理了这件事故与另一种情况：`1,3` 这种非连续节次返回 `null`（让这一行被记为跳过），
而不是折叠成 `1-3` 把没上的课也画进去。

同一类坑还有两个，都值得先看一眼再动手：

| 坑 | 表现 | 处置 |
| --- | --- | --- |
| 周次字段里混着节次（`1-16周[1-2节]`） | 周次解析抛错 | 先用 `weeksOnly` 之类的写法摘掉 `[n-m节]` 再交给 `ctx.parseWeeks` |
| 位图周次里混进了别的字段 | 周次全是错的、而且不报错 | `weeksEncoding` 必须与该部署一致；声明 `bitmap` 但内容不是 0/1 时运行流程会抛错 |

## 9. 隐私与安全（应用侧要求）

脚本在用户的**登录会话里**执行，这几条是硬要求（完整的审阅标准在预设仓库 README 里）：

- 只访问**同源**的教务系统接口。`ctx.http.*` 已在代码里强制同源（传跨源绝对地址直接抛错），
  但审阅时仍要看有没有绕开它的写法。
- **不得**读取、传递或打印学号、姓名、Cookie、凭据。诊断信息只应含字段名与计数——
  试跑摘要就是按这个标准设计的，可以直接贴到公开 Issue 里。
- 不得有任何绕过用户确认直接落库的路径（载荷只有经过确认弹窗才会写入）。
- 任何**写操作**（选课、评教、申请、提交表单）一律不接受。

## 10. 提交前检查

1. `node --test` 与 `pwsh ./tools/Build-SourceIndex.ps1 -Check` 通过（预设仓库 README 第 8 节）。`indexVersion` 由生成器递增，不要手改。
2. **在真实教务系统上跑通过一次完整导入**，并核对了课表内容。没有实测过的条目不要提交。
3. 试跑摘要里的 `跳过的行` 是 0，或每一条原因都解释得清。
4. 确认弹窗里没有「第 N 节未定义」「第 N 周超出」「课时重叠」这类提示，或已确认它们是正确的。
5. `config` 里只写了与族默认值不同的项，且都在 `CHANGEPOINTS.md` 里。
6. `description` 写清了适用系统、使用前提与已知限制。
